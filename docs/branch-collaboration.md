# 分支协作规范（Kiro / GPT）

本仓库由两个 AI 协作者并行开发：**Kiro** 与 **GPT（Codex）**。各自在自己的分支上工作，**不得修改对方归属范围内的文件**。`main` 是受保护的集成分支，只通过合并请求（PR）由仓库所有者合入。

## 1. 分支

| 分支 | 归属 | 用途 |
|------|------|------|
| `main` | 仓库所有者 | 集成与发布基线，受保护，禁止任何一方直接推送 |
| `kiro` | Kiro | Kiro 的长期工作分支；功能分支用 `kiro/<主题>` |
| `gpt` | GPT | GPT 的长期工作分支；功能分支用 `gpt/<主题>`（历史 `codex/*` 分支视为 GPT 所有） |

两条工作分支均从 `main` 切出（基线提交 `97844e0`，即 v1.3.0），完成后各自向 `main` 提 PR。

## 当前阶段：前端比拼

当前阶段，Kiro 与 GPT 的比拼范围**仅限于前端**，即 Android 客户端 `mobile/app/src/**`（界面、交互、动画及其单元测试）。

- 双方各自在自己的分支（`kiro` / `gpt`）上独立完成同一前端需求，只修改 `mobile/app/src/**`，互不读取、合并或修改对方分支。
- 服务端、部署编排、构建配置、发布产物和共享区不在比拼范围内，比拼期间双方都不改动这些文件。
- 由仓库所有者评审双方结果，并决定哪一方的实现以 PR 合入 `main`。
- 第 2 节的文件归属不变，它决定比拼结束后 `main` 上各文件的长期维护方。

## 3. 边界规则

1. 各分支只能新增、修改、删除**自己范围内**的文件。
2. 不得修改对方范围内的文件，包括"顺手"修格式、改拼写、调整导入。
3. 共享区文件只能按第 4 节的流程修改。
4. 不得推送、重写、删除对方的分支，不得在对方分支上提交。
5. 不得直接推送 `main`，不得强制推送任何共享分支。
6. 提 PR 前自检：`git diff --name-only main...HEAD` 列出的每个文件都必须属于本方范围；出现越界文件时，先撤回该改动再提 PR。
7. 版本号（`versionName` / `versionCode`）、标签和 GitHub Release 由发布流程统一处理，GPT 分支不自行修改版本号。

## 4. 跨分支改动的协调方式

需要改动对方范围或共享区的文件时：

1. **提出请求**：在对方可见的位置（PR 描述、Issue，或由仓库所有者转达）写明：要改哪个文件、为什么改、期望的改动内容（最好附 diff 片段）。
2. **由归属方实施**：对方文件只能由对方在自己的分支里修改。共享区文件由提出方在单独的 PR 里修改，PR 标题以 `[shared]` 开头，并在合入前获得仓库所有者确认。
3. **契约优先**：涉及客户端和服务端的接口变更时，先在共享区更新 `docs/api-contract.md`（单独 PR），合入后双方再各自实现。
4. **未合入前不依赖**：一方不得在自己的分支里临时复制或修改对方文件来"先跑通"；可以在本方代码里使用开关或桩实现，等对方改动合入 `main` 后再接入。

## 5. 冲突处理

1. 按本规范划分时，两条分支的改动不应出现文件级重叠。如果出现冲突，说明有一方越界或共享区修改流程没走完。
2. 同步上游时，各分支只把 `main` 合并（或 rebase）到**自己的分支**，不处理对方未合入的改动。
3. 冲突出在本方文件：由本方解决。
4. 冲突出在对方文件：保留对方（即 `main` 上）的版本，撤回本方越界改动；本方确实需要的改动按第 4 节转为请求。
5. 冲突出在共享区文件：暂停合并，交仓库所有者裁决，不要擅自选取任一方版本。
6. 无法判断归属的文件：视为共享区，交仓库所有者裁决，并在本规范中补充归属。

## 6. 规范的修改

本文件属于共享区。调整归属范围需要提 `[shared]` PR，并经仓库所有者确认后生效。
